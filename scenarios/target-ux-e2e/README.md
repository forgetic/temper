# Target UX end-to-end validation bundle

This bundle is the checked-in regression input for the complete target-era
operator lifecycle:

```text
temper init -> temper check -> temper plan -> temper apply -> temper serve
```

It inherits the implicit live `basic-delivery` manifest topology, so
`temper-scenario run` uses real Forgejo, a host `forgejo-runner`, standalone
Temper, and Jig fake-LLM agents. The responsibility-based modules under
`tests/target_ux/` add lower-level hermetic operator-contract tests without
starting another live stack or copying registry, transport, agent-invocation,
or webhook unit suites.

## Inputs and static convergence

The checked-in `standalone-json` and `distributed-yaml` bundles, plus temporary
bundles generated by the tests, prove that:

- top-level and subcommand help promote the public lifecycle while `daemon`,
  `agent`, and `trigger-forgejo` remain dispatchable but unpromoted;
- JSON and YAML workflows pass equivalent static validation through `check`,
  `plan`, the `ApplyProvisioner` apply seam, and bounded `serve` startup loading;
- workflow, state, workspace, and webhook paths resolve relative to the selected
  config bundle;
- explicit `--secrets` wins over systemd `$CREDENTIALS_DIRECTORY`, while a
  same-named systemd credential file overrides its `credentials.toml` entry;
- secret payloads do not appear in human or JSON check, config, plan, apply, or
  startup output;
- generated standalone and distributed pool/profile shapes reach the existing
  runtime adaptation guards for selection and capacity.

## Plan, multi-repository apply, and confirmation

`temper plan` is read-only and reports every `[engine] repos` entry. The target
regression checks both human and JSON reports, including the intentionally
retained singular JSON projection for a one-repository deployment. A generated
two-repository bundle proves that `plan` and `apply` use the same collection.

Without `--yes`, declining the default-no confirmation makes no provisioning
call and leaves credentials unchanged. With `--yes`, apply sends every
repository in one deployment-wide `ApplyPlanRequest`; it does not provision one
repository at a time. Production operators should still review the plan and run
`temper apply --yes` as a separate mutation step. `temper init --apply --yes`
remains a demo convenience.

## Forgejo webhook intake

Operators send HMAC-signed Forgejo events to `POST /forgejo/webhook` on a
configured `temper serve engine` or `temper serve standalone` runtime. Set the
shared signing secret with `[engine] webhook_secret` or
`[engine] webhook_secret_file`. Webhooks accelerate reaction to Forgejo events;
periodic polling remains the correctness backstop if a delivery is delayed or
lost.

`temper trigger-forgejo` is a legacy/internal adapter command retained only for
focused adapter compatibility test coverage. Operator deployments use the
webhook endpoint above. `temper serve trigger` stays rejected with migration
guidance; systemd deployments do not install a trigger unit.

## Responsibility map

- `tests/target_ux/onboarding.rs`: generated init/check/apply and standalone
  runtime adaptation.
- `tests/target_ux/deployment.rs`: JSON/YAML loading, config-relative paths,
  explicit/systemd secret precedence, redaction, plan, multi-repository apply,
  decline, and `--yes`.
- `tests/target_ux/runtime.rs`: distributed offline/fake-online checks and
  bounded pool/profile startup guards.
- `tests/target_ux/webhook.rs`: the checked-in signed payload receives `202`
  from an in-process engine route and the selected/rejected trigger guidance is
  consistent.
- `tests/target_ux/compatibility.rs`: public help, hidden dispatch, docs, and
  audit-matrix citations.
- `tests/target_ux/support.rs`: process and fake-provisioning utilities only.

The broad family deliberately cites rather than clones these focused authorities:

- `no_pool_registration_preserves_legacy_capabilities_even_with_policies`;
- `register_without_pool_preserves_legacy_capabilities_with_pool_policies`;
- `pool_without_agent_profile_uses_legacy_provider_fallback`;
- `legacy_only_config_has_no_target_metadata_and_preserves_runtime_fields`;
- `selected_pool_agent_profile_controls_command_and_env`;
- `posted_webhook_wakes_target_then_worker_is_assigned` and
  `posted_webhook_drives_success_apply_to_pull_request`;
- invalid-signature/malformed webhook route tests and
  `selected_forgejo_contract_accepts_forgejo_headers_and_sha256_prefix` in the
  legacy adapter suite.

Production changes to those internals require a separately reproduced defect
and focused test changes.

## Operator docs and systemd contract

The operator recipe is [`docs/how-to/deploy-with-systemd.md`](../../docs/how-to/deploy-with-systemd.md).
Its checked-in [`examples/systemd/`](../../examples/systemd/) bundle covers
public engine/worker serve commands, every pool/profile credential reference,
and `LoadCredential=credentials.toml:/etc/temper/credentials.toml`. The
normative implementation/test/status mapping is the
[target-era operator contract matrix](../../docs/reference/target-era-operator-contract-matrix.md).

All tokens and passwords under `config/` are fake fixture values. Validate the
complete contract from the repository root with:

```sh
./.temper/pre-pr
cargo dev-scenario-check
```
